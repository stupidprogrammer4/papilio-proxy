# راهنمای پایهٔ آزمایشی

## انتخاب HTTP یا HTTPS در main

اجرای `sudo bash ./install.sh --source "$PWD"` از پوشهٔ سورس، ویزارد ترمینالی را
باز می‌کند. محیط، دامنه/IP و روش دسترسی را مشخص کنید؛ F3 تنظیمات پیشرفتهٔ شناسهٔ
نصب، نشانی شنود، پورت‌ها و روش ایمیج‌ها را بدون پاک‌کردن مقادیر باز و بسته می‌کند. F2 مرور
تنظیمات، Enter ادامه و Esc لغو است. ترمینال ساده فرم متنی دارد. محیط اولیهٔ
bootstrap اکنون production است؛ dev/test/sandbox هم قابل انتخاب‌اند. گزینه‌های
خط فرمان و تنظیمات ذخیره‌شدهٔ نصب قبلی، مقدار اولیهٔ فرم را فراهم می‌کنند.
مرور فرم، قاعدهٔ حفظ نصب موجود را دور نمی‌زند و نصب مجدد را به تغییر تنظیمات تبدیل نمی‌کند.

نصاب سورس فعلی در هر چهار محیط `dev`، `test`، `sandbox` و `production`، گزینهٔ
`--scheme http` یا `--scheme https` را می‌پذیرد. مثلاً از پوشهٔ سورس main:

```sh
sudo bash ./install.sh --source "$PWD" --non-interactive --environment production --host panel.example.com --scheme http
```

همهٔ سرویس‌های فعلی روی همین سرور اجرا می‌شوند. HTTP فقط از `--port` انتخابی
استفاده می‌کند؛ پورت TLS باز نمی‌شود و هدایت اجباری به HTTPS ندارد. برای HTTPS،
گزینهٔ `--scheme https`، دامنهٔ متصل به سرور و دسترسی لازم برای صدور گواهی را
فراهم کنید؛ پورت عمومی TLS با `--https-port` انتخاب می‌شود. انتخاب روش دسترسی وب،
قرارداد جداگانهٔ mTLS عامل نود را تغییر نمی‌دهد. نصب‌های قبلی بدون فیلد scheme،
رفتار قبلی خود را حفظ می‌کنند. این گزینه جدیدتر از نصاب منتشرشدهٔ alpha.1 است.

پنج مرحلهٔ اجرا شامل بررسی پیکربندی، آماده‌کردن ایمیج، اجرای زیرساخت، migration
دیتابیس و بررسی برنامه/worker است. سورس بدون manifest روی سرور build می‌شود.
با `--image-mode auto|prebuilt|build` روش ایمیج‌ها را انتخاب کنید. بستهٔ آماده در
کش نگه داشته می‌شود؛ اندازه و SHA پیش از بارگذاری و شناسه/معماری هر ایمیج پس از
آن بررسی می‌شوند. build و ورود به رجیستری در این مسیر لازم نیست. خطای بسته نصب
را متوقف می‌کند. تغییر روش ایمیج، هویت نصب و کلیدها را عوض نمی‌کند. انتشار رسمی
و آزمون سرور تمیز alpha.3 هنوز باقی است. این نامزد انتشار، هر دو شناسهٔ OCI و
config را برای مخزن‌های Docker دارد. alpha.2 در Docker29 تمیز، مشکل تأییدشدهٔ
شناسه دارد؛ راه‌حل موقت آن انتخاب صریح build است. فایل انتشار قبلی عوض نمی‌شود.

## ساخت مالک

۱. دستور نصب README را اجرا کنید.
۲. آدرس `/setup` نمایش‌داده‌شده را باز کنید.
۳. توکن پنج‌دقیقه‌ای، نام کاربری و رمز قوی را وارد کنید.
۴. پس از ساخت مالک از `/login` وارد شوید. برای توکن تازه، `sudo papilio setup-token`
را روی سرور اجرا کنید.

پس از راه‌اندازی، مسیر ساخت مالک بسته می‌شود. اعتبارسنجی رمز با Django است و حداقل
پیش‌فرض ۱۲ کاراکتر دارد. توکن راه‌اندازی با API key معمولی متفاوت است. API key و
2FA اختیاری هنوز در مراحل بعدی قرار دارند.

## بررسی کارهای پس‌زمینه

صفحهٔ اصلی، وضعیت دیتابیس، کش و آخرین گزارش هر دو worker را نشان می‌دهد. گزارش
تازه، تضمینِ رخ‌ندادن خرابی پس از آن لحظه نیست. بررسی ارتباطی یا پردازشی را بزنید
و با «تازه‌سازی» نتیجهٔ ثبت‌شده را ببینید. فقط کاری که هنوز در صف است از این مسیر
لغو می‌شود. هر ادمین فقط عملیات خودش را می‌خواند یا لغو می‌کند؛ دسترسی لغوشده
اجازهٔ اجرای بررسی تازه ندارد.

## تغییر زمان‌بندی

مالک می‌تواند فاصلهٔ اجرا و فعال‌بودن تحویل پیام و گزارش workerها را در صفحهٔ اصلی
تغییر دهد. تغییرات با scheduler دیتابیس و بدون restart اعمال می‌شوند. ذخیرهٔ نسخهٔ
قدیمی تنظیمات رد می‌شود؛ پیش از تلاش دوباره تازه‌سازی کنید. غیرفعال‌کردن تحویل،
کارها را در صف نگه می‌دارد؛ غیرفعال‌کردن گزارش worker پس از انقضای گزارش قبلی،
وضعیت آمادگی را ناموفق می‌کند.

## فرمان و محیط

لانچر نصب‌شده به محیط و شناسهٔ انتخاب‌شده هنگام نصب اشاره می‌کند. برای انتخاب
نصب دیگر، گزینه‌ها را پیش از نام فرمان بنویسید:

```sh
sudo papilio --environment dev --instance work status
sudo papilio logs worker-io --tail 50 --follow
sudo papilio doctor --timeout 120
```

داده و تنظیمات در `/opt/papilio/ENVIRONMENT/INSTANCE/` هستند. فایل `runtime.env`
خصوصی است. شناسه و مسیرهای تولیدشده باید با `installation.json` هماهنگ بمانند؛
تغییر مسیر به خارج نصب یا واردکردن متغیرهای اجرای میزبان پذیرفته نمی‌شود. تنظیمات
راه‌اندازی معمولاً به restart سرویس مرتبط نیاز دارند.

## پشتیبان‌گیری و بازیابی

```sh
sudo papilio backup --output /private/path/papilio.tar.gz
sudo papilio restore /private/path/papilio.tar.gz
```

آرشیو فشرده شامل دیتابیس، تنظیمات و دادهٔ گواهی Caddy است. این انتشار پایه هنوز
رمزگذاری اختیاری ندارد؛ بکاپ دارای اطلاعات محرمانه است و باید خصوصی نگه داشته
شود. رمزگذاری با رمز دلخواه، چندقسمتی‌کردن، ارسال زمان‌بندی‌شده به تلگرام/دیسکورد
و بازیابی از پنل، ردیف‌های جدا و تکمیل‌نشده‌اند.

بازیابی نسخه، محیط و شناسهٔ سازگار می‌خواهد؛ فایل و checksum را بررسی و ابتدا از
وضعیت فعلی بکاپ می‌گیرد. سپس سرویس‌های برنامه متوقف می‌شوند و بازیابی با نقش
دیتابیس بدون دسترسی superuser انجام می‌شود. کلید برنامه بازیابی می‌شود ولی
اعتبارنامه‌ها و مسیرهای زیرساخت مقصد حفظ می‌شوند. پیام‌های صف همین نصب پاک و
عملیات در انتظار از outbox دیتابیس پیگیری می‌شوند. اگر شکست خورد، بکاپ پیش از
بازیابی را حفظ و لاگ‌ها را بررسی کنید؛ شکست، موفقیت اعلام نمی‌شود.

## به‌روزرسانی

```sh
sudo papilio update
sudo papilio update --version VERSION
sudo papilio update --source /opt/papilio/releases/papilio-NEW_VERSION
```

فقط نسخهٔ منتشرشده قابل دریافت است. نصاب خود نسخهٔ مقصد پیش از migration بکاپ
می‌گیرد و ایمیج‌ها را آماده می‌کند. روش ایمیج قبلی حفظ می‌شود مگر با
`update --image-mode MODE` آن را تغییر دهید. برای نصاب قدیمی، bootstrap جدید
گزینهٔ `--update` دارد؛ محیط، شناسه و مسیر نصب قبلی را بدهید و نیازی به دامنه
و پورت دوباره نیست.
سازگاری ارتقای هر انتشار باید جداگانه آزموده شود. مهاجرت از پیاده‌سازی حذف‌شده
جزو این بازسازی نیست. `stop` داده‌ها را حذف نمی‌کند و `status` صرفاً وضعیت را می‌خواند.

## ثبت نود در main (جدیدتر از alpha.1)

۱. با حساب مالک وارد «نودها» شوید. نام و نشانی HTTPS عامل را وارد کنید. در تنظیمات
پیشرفته، نشانی شنود و API محلی، مهلت‌ها، محدودیت بایت و عمر گواهی را انتخاب کنید.
مقادیر برای همان نود ذخیره می‌شوند و پیش‌فرض فرم از بک‌اند دریافت می‌شود.

۲. نود را ثبت و تازه‌سازی کنید تا صدور گواهی موفق شود. worker پردازشی برای هر نود
مرجع صدور و گواهی سرور و کنترل می‌سازد. وضعیت اتصال تا اجرای بررسی واقعی، «بررسی
نشده» باقی می‌ماند؛ صدور گواهی به معنی آنلاین‌بودن نود نیست.

۳. فایل خصوصی راه‌اندازی را دانلود کنید. شامل `agent.json`، `server.crt`، `server.key`
و گواهی عمومی `client-ca.crt` است؛ کلید خصوصی مرجع و کنترل پنل در آن نیست. فایل‌ها
را محرمانه و در پوشه‌ای خصوصی کنار عامل قرار دهید. روش ساخت و اجرای عامل در
[راهنمای عامل](../node/agent/README.fa.md) است. Xray باید از قبل با API روی loopback
اجرا شده باشد؛ این مرحله نصب خودکار هسته نیست.

۴. «بررسی اتصال» و سپس «تازه‌سازی» را بزنید. worker ارتباطی پس از بررسی مرجع صدور،
نام میزبان و هویت نود و نصب، زمان اجرای زندهٔ Xray را می‌خواند. موفقیت این بررسی
به معنی ساخت اشتراک یا پشتیبانی از سایر قابلیت‌های هسته نیست.

زمان‌بند «ارسال عملیات نود» در صفحهٔ اصلی، روشن/خاموش و فاصلهٔ قابل تغییر دارد.
غیرفعال‌کردن آن اسکن‌های بعدی outbox را متوقف می‌کند؛ کار قبلاً ارسال‌شده ممکن است
تمام شود. مهاجرت و restart انتخاب کاربر را حفظ می‌کنند. مقادیر راه‌اندازی هنگام
شروع عامل اعمال می‌شوند. ویرایش نود موجود، تمدید و چرخش گواهی و نصب خودکار هنوز
باقی مانده‌اند. کلید خصوصی نصب را همراه بکاپ نگه دارید؛ رمزگشایی کلیدهای نود پس
از بازیابی به آن وابسته است.

## راه‌اندازی بات هر اپراتور در main (جدیدتر از alpha.1)

۱. بات را در BotFather بسازید، سپس در پاپیلیو «بات‌های تلگرام» را باز کنید. نام و
توکن را وارد کنید. توکن رمز‌شده ذخیره می‌شود و در فهرست یا جزئیات بازگردانده نمی‌شود؛
پس از ذخیرهٔ موفق، فیلد توکن خالی خواهد شد.

۲. دریافت پیام را فعال و فاصلهٔ زمان‌بند را انتخاب کنید. تنظیمات پیشرفته شامل نشانی
API، مهلت انتظار پیام و HTTP، اندازهٔ بسته و پاسخ، عمر لینک اتصال و تأخیر پس از خطا
است. پیش‌فرض فقط مقدارِ واردنشده هنگام ساخت را پر می‌کند؛ مهاجرت، بازیابی و restart
تنظیم شما را حفظ می‌کنند. توکن جایگزین خالی، توکن فعلی را حفظ می‌کند.

۳. تازه‌سازی کنید تا هویت بات تأیید شود. بررسی در worker ارتباطی اجرا می‌شود. اگر
webhook قبلی وجود داشته باشد، گزارش می‌شود و حفظ خواهد شد؛ پیش از انتخاب این روش
دریافت، خودتان آن را حذف کنید. دریافت‌کنندهٔ هم‌زمان، توکن نامعتبر یا خطای ارتباط
همراه زمان تلاش بعدی نمایش داده می‌شود. توکن جایگزین باید متعلق به همان بات باشد؛
بات متفاوت را جدا ثبت کنید.

۴. «ساخت لینک اتصال ادمین» را بزنید. لینک را محرمانه نگه دارید، در تلگرام باز کنید
و Start بزنید. با تازه‌سازی، چت متصل را می‌بینید؛ نیازی به واردکردن دستی `chat_id`
نیست. لینک زمان انقضا دارد و یک‌بارمصرف است؛ ساخت لینک تازه، لینک قبلی را باطل می‌کند.
اتصال تنها از چت خصوصی با شناسهٔ فرستنده و چت یکسان پذیرفته می‌شود.

۵. تنظیمات بات انتخاب‌شده را ویرایش کنید. تازه‌سازی وضعیت، فرم و نسخهٔ آن را حفظ
می‌کند. برای دریافت تغییرات ویراستار دیگر، «بارگذاری مجدد و کنارگذاشتن فرم» را بزنید؛
ذخیرهٔ نسخهٔ قدیمی رد می‌شود. غیرفعال‌کردن دریافت پیام مانع تماس‌های بعدی می‌شود؛
درخواست در حال اجرا می‌تواند تمام شود ولی نتیجهٔ قدیمی تنظیمات جدید را بازنویسی نمی‌کند.

این مرحله راه‌اندازی بات و دریافت پایدار پیام‌های پشتیبانی‌شده را پوشش می‌دهد.
منوی خرید، تأیید رسید، کیف پول، تحویل خرید و دریافت مستقل هنگام قطعی هنوز تکمیل نشده‌اند.
این قابلیت‌های جدید در بستهٔ alpha.1 نیستند.

## ثبت هستهٔ Xray در main

این API توسعه، به Xray موجود روی نود ثبت‌شده اشاره می‌کند. شناسهٔ نود را از
پاسخ ثبت قبلی بگیرید. عامل mTLS و هسته باید از قبل اجرا شده باشند؛ این عملیات
آن‌ها را نصب نمی‌کند. درخواست‌ها از نشست مالک و هدر CSRF عادی استفاده می‌کنند.

| روش | مسیر | ورودی / نتیجه |
| --- | --- | --- |
| POST | `/api/v1/cores/xray` | `request_key` از نوع UUID، `node_id`، `name` و مقدار اختیاری `default_user_level` با پیش‌فرض صفر؛ شناسهٔ هسته برمی‌گردد. |
| GET | `/api/v1/cores` | جست‌وجو با `q`، `page` و `page_size` روی کل مجموعهٔ مجاز. |
| GET | `/api/v1/cores/{core_id}` | اطلاعات هسته و پیش‌فرض‌های Xray. |
| POST | `/api/v1/cores/{core_id}/xray/inbounds` | `request_key`، تگ موجود `tag`، نشانی `public_host` و `port`؛ شناسهٔ inbound برمی‌گردد. |
| GET | `/api/v1/cores/{core_id}/xray/inbounds` | جست‌وجوی صفحه‌بندی‌شدهٔ تگ‌ها. |
| GET | `/api/v1/cores/{core_id}/xray/inbounds/{inbound_id}` | خواندن inbound متعلق به همان هسته. |

نمونهٔ اولیهٔ endpoint برای VLESS/TCP بدون TLS است. تگ باید در تنظیمات واقعی
هسته موجود باشد. نشانی و پورت برای اتصال کلاینت هستند. چند تگ برای یک هسته
ثبت می‌شود؛ قرارداد فعلی عامل، یک فرایند Xray روی هر نود را آدرس‌دهی می‌کند.

پس از خطای ارتباط، همان کلید درخواست و همان تنظیمات را تکرار کنید. ثبت تازه
۲۰۱ و تکرار بدون تغییر ۲۰۰ می‌دهد. تنظیمات متفاوت با همان کلید یا هویت تکراری
هسته ۴۰۹ می‌دهد؛ نود، هسته و فرزند خارج از مالکیت با ۴۰۴ پنهان می‌شوند.
بیشترین مقدار سطح کاربر در قرارداد خود Xray برابر ۴۲۹۴۹۶۷۲۹۵ است.

`PAPILIO_MAX_PAGE_SIZE` سقف معتبر هر صفحه برای APIهای جدید است؛ پیش‌فرض ۲۰۰
دارد و تغییرش به restart پردازش API نیاز دارد. ویرایشگر پنلی آن و ویرایش هسته
و inbound هنوز باقی است؛ ثبت اطلاعات به معنی مدیریت کامل هسته نیست.

## نمونهٔ پایدار ساخت سرویس در main

این بخش توسعه، سرویس نامحدود VLESS/TCP را از inbound موجود می‌سازد. شناسه‌های
هسته و inbound از پاسخ‌های مرحلهٔ قبل گرفته می‌شوند. صفحهٔ «سرویس‌ها»ی مالک
به همین API متصل است؛ گردش خرید بات هنوز باقی است.

### استفاده از پنل

۱. صفحهٔ «سرویس‌ها» را باز کنید. هستهٔ ثبت‌شده را انتخاب کنید یا «ثبت Xray
موجود» را باز کنید، نود آن را انتخاب و نام را وارد کنید. سطح پیش‌فرض کاربر در
تنظیمات پیشرفته قابل انتخاب است. عامل نود و Xray باید از قبل اجرا شده باشند.

۲. ورودی ثبت‌شده را انتخاب کنید یا «ثبت ورودی موجود» را باز کنید و تگ دقیق
ورودی VLESS/TCP بدون TLS، نشانی عمومی و پورت کلاینت را وارد کنید. این کار
اطلاعات ورودی موجود را ثبت می‌کند و ورودی جدیدی در هسته نمی‌سازد.

۳. نام سرویس را وارد و «ساخت سرویس» را انتخاب کنید. تنظیمات پیشرفته اجازهٔ
انتخاب سطح کاربر و UUID را می‌دهد؛ مقدار خالی یعنی پیش‌فرض ثبت‌شدهٔ هسته و
تولید امن اعتبارنامه.

۴. با «به‌روزرسانی» نتیجهٔ واقعی ساخت را بخوانید. پس از موفقیت «دریافت لینک
اشتراک» را بزنید. کادر لینک در HTTP و HTTPS برای کپی قابل انتخاب است؛ دارندهٔ
این لینک خصوصی به اطلاعات اتصال دسترسی دارد.

همهٔ فهرست‌ها جست‌وجو، تعداد نتیجه و صفحه‌بندی دارند. انتخاب فعلی با جست‌وجو
یا عوض‌کردن صفحه حفظ می‌شود. رکورد تازه خودکار انتخاب می‌شود و نیازی به واردکردن
دوبارهٔ شناسه ندارد. سرویس موجود پس از بازکردن دوبارهٔ صفحه هم قابل انتخاب است.
صفحه و منوی سرویس‌ها دسترسی فعلی مالک را بررسی می‌کنند؛ کارمند عادی این دسترسی
را ندارد. زبان فارسی و انگلیسی در پنل قابل انتخاب است.

### استفاده از API

۱. به `/api/v1/services` با POST، مقادیر `request_key` از نوع UUID، `name`،
`core_id` و `inbound_id` را بدهید. ورودی‌های پیشرفتهٔ اختیاری `identifier`
از نوع UUID و `user_level` هستند. اعتبارنامهٔ خالی تولید می‌شود و سطح انتخابی
یا پیش‌فرض مؤثر روی همان سرویس ذخیره می‌شود.
۲. پاسخ ۲۰۲ شناسهٔ سرویس و وضعیت اجرای `queued` را برمی‌گرداند. با GET روی
`/api/v1/services/{id}` تعداد تلاش، خطای آخر و نتیجهٔ worker را بخوانید.
ثبت سرویس و outbox قبل از ارتباط خارجی در یک تراکنش انجام می‌شوند.
۳. پس از `succeeded` شدن، با GET روی `/api/v1/services/{id}/subscription`
آدرس امضاشدهٔ کلاینت را بگیرید. وضعیت در انتظار، ۴۰۹ می‌دهد. آدرس عمومی،
اشتراک Base64 شامل لینک VLESS را برمی‌گرداند و دسترسی به تنظیم همان سرویس می‌دهد.
۴. GET روی `/api/v1/services` جست‌وجوی `q` و صفحه‌بندی `page` و `page_size`
دارد. سرویس دیگران و ترکیب نادرست هسته و inbound با ۴۰۴ پنهان می‌شوند.

پس از خطای ارتباط، همان کلید و ورودی‌ها را تکرار کنید؛ اعتبارنامه و سطح اولیه
حفظ می‌شوند و درخواست متعارض ۴۰۹ می‌دهد. قطعی RabbitMQ درخواست ثبت‌شده در
دیتابیس را حذف نمی‌کند و پس از بازیابی، outbox آن را تحویل می‌دهد.

در صفحهٔ وضعیت، «ارسال درخواست ساخت سرویس» فعال‌بودن و فاصلهٔ زمان‌بندی را
بدون restart تغییر می‌دهد. مقدار اپراتور با مقداردهی اولیه بازنویسی نمی‌شود.
کاری که قبلاً ارسال شده یا در حال اجراست می‌تواند تمام شود.

`status` نتیجهٔ آخرین ساخت اولیه است و سلامت دائمی هسته را تضمین نمی‌کند.
بازسازی خودکار کاربران پس از restart هسته هنوز پیاده نشده؛ رکورد سرویس و
اعتبارنامه در PostgreSQL می‌مانند. سهمیه، انقضا، چرخهٔ تغییر سرویس، قالب‌های
دیگر اشتراک، فروش و تحویل بات هنوز برای تکمیل MVP فروش لازم‌اند.
بستهٔ منتشرشدهٔ alpha.3 این API توسعه و صفحهٔ سرویس‌ها را ندارد.

## حساب مشتری و کیف پول در main

در «مشتریان و کیف پول» حساب متعلق به اپراتور بسازید یا جست‌وجو کنید. حساب تازه
خودکار انتخاب می‌شود. کیف پول IRR را صریحاً ایجاد کنید؛ برای حساب فاقد کیف پول،
موجودی فرضی نمایش داده نمی‌شود. تمام مبلغ‌ها **ریال (IRR)** هستند.

«سقف اعتبار به ریال» در ابتدا صفر است و خرج بیشتر از موجودی را مجاز نمی‌کند.
مقدار مثبت، بدهی تا همان سقف را صریحاً مجاز می‌کند. ویرایش آن از پنل بدون restart
اعمال می‌شود. کاهش سقف به کمتر از بدهی فعلی رد می‌شود؛ برای ویرایش هم‌زمان باید
نسخهٔ فعلی را به‌روزرسانی کنید. ایجاد دوبارهٔ کیف پول موجود انتخاب اعتبار را
با مقدار پیش‌فرض جایگزین نمی‌کند.

«تغییر دستی موجودی» افزایش یا کاهش کیف پول انتخاب‌شده را با دلیل اجباری ثبت
می‌کند. اپراتور، مبلغ، زمان و موجودی قبل و بعد نگه داشته می‌شود. تکرار درخواست
قطع‌شده با UUID و جزئیات یکسان فقط یک اثر دارد؛ جزئیات متفاوت با همان UUID خطای
۴۰۹ می‌دهد. اعتبار ناکافی یا سرریز، هم موجودی و هم دفتر را بدون تغییر می‌گذارد.
جست‌وجو و صفحه‌بندی تمام سوابق مجاز را پوشش می‌دهد؛ نشانی سند یک مشتری را نمی‌توان
برای کیف پول مشتری دیگری استفاده کرد.

فعلاً این کنترل‌ها متعلق به مالک فعال‌اند و کارمند عادی دسترسی ندارد. این بخش
پایهٔ حسابداری است و مسیر خرید پایین از همین دفتر برداشت می‌کند. تأیید رسید،
تطبیق بانک و گردش رسمی بازپرداخت هنوز باقی‌اند. بستهٔ alpha.3 این بخش توسعه را ندارد.

### API مشتری و کیف پول

| روش | مسیر | عملیات |
| --- | --- | --- |
| POST | `/api/v1/customer-accounts` | ساخت با `request_key` از نوع UUID و `name`؛ ساخت ۲۰۱ و تکرار ۲۰۰. |
| GET | `/api/v1/customer-accounts` | جست‌وجو با `q`، `page` و `page_size`. |
| GET | `/api/v1/customer-accounts/{customer_id}` | خواندن حساب متعلق به مالک. |

| GET | `/api/v1/customer-accounts/{customer_id}/wallet` | خواندن کیف پول؛ نبودن کیف پول ۴۰۴ است. |
| PUT | `/api/v1/customer-accounts/{customer_id}/wallet` | تغییر `credit_limit_minor` با `expected_revision`. |

| GET | `/api/v1/customer-accounts/{customer_id}/wallet/entries` | جست‌وجوی دلیل اسناد با `q`، `page` و `page_size`. |
| GET | `/api/v1/customer-accounts/{customer_id}/wallet/entries/{entry_id}` | خواندن سند متعلق به همان کیف پول و مشتری. |

مبلغ‌ها، سقف اعتبار و نسخهٔ تنظیمات در JSON **رشتهٔ عدد صحیح ده‌دهی** هستند تا
BIGINT در JavaScript دقتش را از دست ندهد؛ مثلاً `"9007199254740993"` دقیق می‌ماند.
واحد پشتیبانی‌شده `IRR`/`rial` است. هر مبلغ مثبت حداکثر `9223372036854775807`
است؛ ورودی کسری، نماد علمی، boolean و float رد می‌شوند. موجودی از BIGINT و سقف
اعتبار انتخاب‌شده عبور نمی‌کند. این محدودیت فنی، سقف تعداد حساب یا مشتری نیست.
فیلد معمولی مشتری نمی‌تواند موجودی، مالک یا ثبت‌کنندهٔ سند را تغییر دهد.

## محصول و خرید سرویس در main

در «محصولات»، هسته و ورودی موجود را انتخاب کنید، نام و قیمت ریالی بدهید و
فعال‌بودن برای خرید جدید را تعیین کنید. سطح کاربر Xray اختیاری است؛ مقدار خالی،
پیش‌فرض فعلی هسته را هنگام ذخیرهٔ پیشنهاد ثبت می‌کند. ذخیرهٔ ویرایش، نسخهٔ ثابت
جدیدی می‌سازد؛ قیمت، انتخاب هسته/ورودی و سطح سفارش‌های قبلی حفظ می‌شوند. «محصول جدید» رکورد
جدا می‌سازد و انتخاب شناخته‌شدهٔ هسته و نود را حفظ می‌کند. محصولات اولیه سرویس
نامحدود VLESS/TCP بدون TLS می‌سازند؛ حجم، زمان، تمدید و قیمت پلکانی هنوز اعمال نمی‌شوند.

در «مشتریان و کیف پول»، مشتری را انتخاب کنید، برای محصول پولی موجودی/اعتبار کافی
داشته باشید، محصول و نام سرویس را مشخص و «خرید و ساخت سرویس» را بزنید. سفارش،
یک برداشت و درخواست ساخت سرویس/outbox در یک تراکنش PostgreSQL ثبت می‌شوند.
اعتبار ناکافی سفارش تازه را هم برمی‌گرداند. قیمت صفر خرید رایگان می‌سازد و به
کیف پول یا سند مالی نیاز ندارد.

مبلغ نمایش‌داده‌شده، قرارداد مالی پذیرفته‌شده است. ساخت واقعی سرویس در پس‌زمینه
ادامه دارد؛ «به‌روزرسانی» نتیجهٔ واقعی را می‌خواند و پس از موفقیت «دریافت لینک
اشتراک» فعال می‌شود. قطعی RabbitMQ سفارش، برداشت و سرویس صف‌شده را حذف نمی‌کند.
خطای هسته برای پیگیری اپراتور دیده می‌شود؛ بازپرداخت خودکار، بازیابی کامل چرخهٔ
سرویس و تسویهٔ رسید هنوز باقی‌اند. تغییر مشتری، سفارش و لینک قبلی را از نمایش
خارج می‌کند؛ فهرست سفارش به مشتری انتخاب‌شده محدود است و صفحه‌بندی و جست‌وجو دارد.

خرید جدید، نسخه و فعال‌بودن فعلی محصول را بررسی می‌کند. درخواست قطع‌شده را با
UUID و ورودی یکسان تکرار کنید: حتی پس از تغییر قیمت/فعال‌بودن/پیش‌فرض‌ها، همان
سفارش بدون برداشت یا سرویس تازه برمی‌گردد. تغییر مشتری، محصول، نسخه یا نام با
همان UUID خطای ۴۰۹ می‌دهد. برای خرید تازه، پیشنهاد تغییرکرده را دوباره بررسی کنید.

بخوانید. مالکیت نود/هسته/ورودی و مشتری در مسیر واقعی برنامه بررسی می‌شود و انتخاب
فرانت مجوز دسترسی ایجاد نمی‌کند. این کنترل‌ها فعلاً برای مالک فعال‌اند؛ بستهٔ
منتشرشدهٔ alpha.3 مسیر خرید توسعه را ندارد.
